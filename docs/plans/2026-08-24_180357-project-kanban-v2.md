# Project Kanban v2 Implementation Plan

> **For Hermes:** Implement one vertical slice at a time with Ponytail `full`. Reuse the native Kanban board and the existing Project Kanban plugins. Do not commit, push, migrate shared vault data, archive real cards, or change the live cron job without explicit user approval.

**Goal:** Evolve Project Kanban v1 into one project-management surface where Obsidian owns project truth, the native Hermes Kanban owns local actions, GitHub and device snapshots provide evidence, and the Inbox remains hosted only on the office desktop.

**Architecture:** Keep the existing `project-kanban` Desktop route, scoped backend plugin, native `todos` board, and office `inbox` board. Add a read-only Projects view to the existing route. Replace generated per-device project-note trees and laptop task hydration with one deterministic JSON observation snapshot per device. Join records by stable `project_id`; never group projects by device.

**Tech stack:** Existing plain ESM Desktop plugin (`@hermes/plugin-sdk`, React), existing Python/FastAPI backend plugin, Python standard library, native Hermes Kanban CLI/database, Git CLI, and the existing `light-lab` theme. No new dependency, service, MCP server, database, or source patch.

**Branch:** `feat/project-kanban-v2`

**Approved visual evidence:** `sketches/project-kanban-v2/index.html`

## 1. Product contract frozen by the approved MVP

### One existing surface, not a second dashboard

- Keep plugin id `project-kanban`, route `/project-kanban`, and sidebar label **Kanban**.
- Board is the default view.
- The route contains three views: **Board**, **Projects**, and **Office Inbox**.
- Keep the v1 four-lane board: **Next**, **Doing**, **Waiting**, and **Review**.
- Preserve v1 card density, category color, source badges, priority tags, move controls, add-action form, responsive lanes, and docked card detail.

### Authority boundaries

```text
Obsidian canonical project note = project status, goal, next action, blocker
Native Hermes `todos` board    = local action workflow
GitHub                         = development activity evidence
Device snapshot                = last-observed and local Git evidence
Office Desktop `inbox` board   = capture and candidate review
```

- GitHub activity never changes project status or progress.
- Device observations never create projects or actions.
- Local Kanban moves never write to Obsidian or Git.
- Only the office desktop turns GitHub/device signals into Inbox candidates.
- Other devices show an honest office-Inbox boundary; they do not clone or synchronize the queue.

### Projects view

- Show one global list of canonical projects; never group or count by device.
- Initial managed set: the eight current notes marked active and explicitly promoted with `project_id`.
- Project detail is read-only and prioritizes:
  1. Obsidian goal, next action, and blocker;
  2. GitHub activity;
  3. device evidence.
- Primary project action is **Open in Obsidian**.
- Show device provenance as **Last observed on `<device>`**, never “updated from.”
- Mark observation evidence stale after seven days.
- **Unmatched** is a read-only derived list. It cannot create projects or Inbox cards.

### Action-to-project link

- A new human action selects a canonical project.
- Store `project_id` inside the existing `project_kanban` JSON metadata in the native task body; do not add a second task schema.
- Derive the action’s category from the linked project.
- Existing v1 cards without `project_id` remain usable and appear as unlinked; no destructive card rewrite is required.

## 2. Minimum data contracts

### Canonical Obsidian project note

Human-named file: `Projects/<title>.md`

Frontmatter:

```yaml
project_id: prairie-drought
knowledge_status: active
project_category: main-research
github_repo: example-lab/prairie-drought  # optional
updated: 2026-08-24                       # optional evidence only
```

Body headings:

```markdown
## Goal
...

## Next action
...

## Blocker
...
```

Rules:

- `project_id` is stable, unique, human-readable kebab-case.
- A note without `project_id` is not a managed project.
- `knowledge_status` remains authoritative.
- `project_category` must be one of `main-research`, `student-projects`, or `systems-admin`.
- Missing optional GitHub data does not exclude a project.
- Device and Git state never get written into the canonical note.

### Device observation snapshot

Path: `Observations/devices/<device>.json`

Minimum shape:

```json
{
  "schema_version": 1,
  "device": "MacLaptop-new",
  "observed_at": "2026-08-24T08:00:00-05:00",
  "projects": [
    {
      "project_id": "prairie-drought",
      "github_repo": "example-lab/prairie-drought",
      "activity_at": "2026-08-23T18:42:00-05:00",
      "head": "abc1234",
      "dirty_count": 3,
      "ahead": 1,
      "behind": 0
    }
  ],
  "unmatched": []
}
```

Rules:

- Sort project and unmatched rows deterministically.
- Publish no absolute path, username, secret, token, raw diff, or file content.
- Match Git repositories automatically by normalized GitHub remote.
- Map non-Git projects only through a machine-local `~/.hermes/project-map.json` entry.
- Folder-name matching is prohibited.
- A snapshot reports observation and local Git facts only.
- Stage and commit only the current device’s snapshot path.

## 3. Non-goals

- No second Projects dashboard, plugin, route, installer, project registry, task database, or theme system.
- No cross-device Kanban synchronization.
- No project entry per local folder, repository clone, or device.
- No device filter or device-based project navigation.
- No Git hooks to stamp commits with machine identity.
- No claim about which device authored a Git commit.
- No automatic project creation from folders or GitHub repositories.
- No automatic task creation from device observations.
- No laptop copy of the office Inbox.
- No new background agent; observation publication remains deterministic and no-agent.
- No new dependency or generic migration framework for eight notes.

## 6. Risks and guardrails

| Risk | Guardrail |
|---|---|
| Canonical notes are malformed | Exclude invalid notes, expose warnings, never invent status/category |
| Same project appears twice | Reject duplicate `project_id`; do not merge by title |
| Device provenance is overstated | Label only “Last observed on”; activity and observation times remain separate |
| Snapshots leak machine paths | Schema allowlist plus tests forbidding home path/username |
| Snapshot job stages unrelated vault work | Path-scoped add/diff/commit only |
| Existing local cards are lost | Legacy cards stay usable; destructive archive is a separate reviewed gate |
| Office Inbox is affected | Detect availability by local board existence; never sync or mutate it remotely |
| Old-laptop data is deleted prematurely | Require a fresh replacement snapshot; otherwise hide legacy notes from UI and preserve them |
| Prototype code becomes production debt | Reimplement with existing components; never import the HTML sketch |
| Branch mixes rejected experiments with v2 | Slice 0 reconciles the dirty tree before feature work |
