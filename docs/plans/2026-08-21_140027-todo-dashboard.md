# Hermes Todo Dashboard Implementation Plan

> **For Hermes:** Implement this plan one vertical slice at a time. Keep Ponytail `full` active: reuse built-ins first, add the minimum code, and do not commit or push without explicit user approval.

**Goal:** Add a private Todo Dashboard to Hermes Desktop that makes the next useful action obvious, supports fast task capture and updates, and optionally turns trusted calendar, mail, messaging, project, cron, and Git signals into a reviewable inbox.

**Audience:** One faculty workspace owner managing personal, research, teaching, and student-related commitments.

**Success:** The dashboard is useful with manual todos alone. On opening it, the user can see what needs action today, why it matters, what is waiting, and what can be deferred. External integrations add context without becoming required dependencies or silently mutating outside systems.

**Architecture:** Preserve the existing `research-dashboard` unchanged and add an independent `todo-dashboard` Desktop plugin with its own route, pane, data, and scoped backend. Keep the repository as the source of truth for dashboard-owned records. Treat Hermes Projects, sessions, cron, local Git, and an approved Microsoft 365 connector as optional inputs that produce inbox candidates or contextual status—not as owners of the todo model.

**Tech stack:** Plain JavaScript ESM Desktop plugin (`@hermes/plugin-sdk`, React, `react/jsx-runtime`), Python standard library plus existing Hermes/FastAPI plugin APIs, JSON data, Hermes cron, Git CLI, an optional pinned Microsoft 365 MCP connector, and the existing `vscode-light-lab` skin.

## 1. Confirmed product direction

### Core job and product identity

- Product name and sidebar label: **Todo Dashboard**.
- Plugin id: `todo-dashboard`.
- Route: `/todos`.
- Pane id: `todo-dashboard:dashboard`.
- The dashboard is a daily work queue, not an agent persona and not primarily a morning briefing.
- It must work fully before Outlook, calendar, Slack, Telegram, cron, or Git integrations are configured.
- Restore it as a pinned pane in the saved layout without navigating or stealing focus.
- Preserve the existing Research Dashboard plugin, route, pane, sidebar entry, status item, and fictional demo unchanged.
- Use native Hermes components, theme variables, and the active `vscode-light-lab` skin.

### Information hierarchy

The default dashboard view is ordered by actionability:

1. **Today** — overdue, due today, timed, blocked, and explicitly pinned work.
2. **Upcoming** — the next seven days, followed by later dated work.
3. **Waiting / Blocked** — commitments that cannot move without another person, event, or decision.
4. **Inbox** — unreviewed manual captures and candidates from optional sources.
5. **Projects** — compact project health and next-action context, not a second project database.
6. **Decisions** — items that need approval, changes, or deferral.

The first viewport should answer three questions without expanding a card:

- What needs my attention now?
- Why is it here?
- What is the next action?

### Todo behavior

- Time buckets: Today / Upcoming / Later.
- Workflow states: Inbox / Next / Doing / Waiting / Blocked / Done.
- Overdue items remain in Today until completed, rescheduled, or explicitly deferred.
- Undated items remain in Inbox or are manually assigned to a bucket.
- Required fields: stable id, title, state, created timestamp, updated timestamp.
- Optional fields: description, project, owner, due date/time, time bucket, priority, waiting-on, source links, source fingerprint, completion timestamp.
- Quick actions: complete, change state, reschedule, pin/unpin, open details.
- Creation must require only a title; advanced fields stay optional.
- Done items remain folded and visible for 30 days, then remain searchable in the archive. Implement the 30-day rollover and archive search in Slice 2; do not let this fall through as unimplemented spec.
- Undo is available after completing, rescheduling, or dismissing an item.
- Completing a pinned item unpins it; completing does not require a separate unpin action.

### Deterministic prioritization

Order actionable items by:

1. overdue timed events and explicit deadlines;
2. due-today work;
3. blockers and people waiting on the user;
4. direct requests or questions;
5. pinned work;
6. stale active projects without a next action;
7. upcoming and routine work.

Tie-break by due timestamp, then updated timestamp, then stable id. Every source-derived item must show a short reason and source badge. Do not use an opaque numeric AI score in v1.

### Projects and decisions

- Reuse Hermes Projects as the explicit repository allowlist; do not create a competing project registry.
- Project context: owner, health, next milestone, blocker, next action, last updated.
- Health values: On track / At risk / Blocked / Waiting.
- Flag an active project as stale after 14 days without an update.
- Local Git context: dirty files, ahead/behind, current branch, last commit, and stale activity.
- Decision context: requester, deadline, options, recommendation, impact, related project, and source.
- Decision actions: Approve / Request changes / Defer, with an optional note.
- External messages, email, calendar, and repository mutations always require a separate explicit user action and approval.

### Optional source model

Optional sources may propose inbox candidates or add context to existing todos:

- Hermes Projects and local Git status.
- Hermes cron health.
- Slack and Telegram conversations that already reached Hermes sessions.
- Outlook mail and calendar through an approved read-only connector.
- Existing session history and source timestamps.

Source rules:

- Never turn a source signal directly into a persistent todo without confirmation.
- Merge likely duplicates into one inbox candidate with visible source badges; allow manual split.
- Store action summaries, provider ids, fingerprints, and links—not full mail bodies or chat transcripts.
- Read complete relevant mail threads when triaging; do not classify from snippets alone.
- Include direct requests, deadlines, meeting preparation, and messages from Important People.
- Exclude newsletters and routine automated notifications by default.
- Remember dismissed, handled, and snoozed source candidates.
- Resurface a candidate only after a material source update or snooze expiry.

### Refresh and scheduled summary

- Render saved local data immediately; optional source refresh must not block the dashboard shell.
- Refresh when the pane opens only if the saved source snapshot is stale.
- Default stale threshold: 15 minutes, configurable later if evidence warrants it.
- Provide a visible manual Refresh action with one in-flight guard and a cooldown.
- Retain last-good source data with a Stale badge and timestamp after failure.
- Keep the existing weekday 9:30 AM America/Chicago job `8d92c7208605`, but rename its purpose to **Todo Dashboard Daily Briefing** when that integration slice is approved.
- The scheduled summary is optional enhancement, not the primary product surface.
- Fetch source changes since the last successful refresh, capped at seven days after weekends or outages.

### UX states and copy

- **Happy:** show task groups with counts, compact next-action cards, and quick actions.
- **Empty:** show “Nothing needs action” with primary **Add todo** and secondary **Review inbox** actions; do not show empty table chrome.
- **Loading:** show saved todos immediately and mark optional source regions “Refreshing…” without disabling todo actions.
- **Failure:** keep local todos usable and show the failed source, last success time, and **Retry**.
- **Stale:** retain last-good source context with a visible Stale badge; never present stale data as current.
- **Constraint:** narrow layouts replace columns with count-labeled tabs while preserving the same actions and ordering.
- **Accessibility:** all actions are keyboard reachable, focus remains on the initiating control after non-navigating updates, status changes are announced, and color is never the only state indicator.

### Data, privacy, and Git policy

- Track dashboard-owned operational data in this private repository.
- Exclude secrets, auth files, raw message bodies, session databases, and sensitive notes not required for action context.
- Validate every write and replace files atomically.
- Dashboard writes may leave the repository dirty.
- Never auto-commit or auto-push.
- Commit or push only after an explicit user request.

## 2. Scope and iteration layering

### Iteration 1: dependable manual todo loop

**Outcome:** A user can open the Todo Dashboard, create a todo, see it in the correct group, update it, complete it, undo the change, and reload without losing state.

**Includes:** validated local data, scoped backend reads/writes, core responsive UI, empty/loading/error states, installer support, and coexistence with Research Dashboard.

**Defers:** source ingestion, Microsoft 365, scheduled summaries, Ask Hermes, and automatic candidate extraction.

### Iteration 2: built-in Hermes context

**Outcome:** Hermes Projects, cron, local Git, and existing Hermes session signals appear as contextual status or reviewable inbox candidates without changing the manual todo source of truth.

**Includes:** deterministic normalization, deduplication, source health, stale fallback, filters, Projects, Decisions, and Ask Hermes.

**Defers:** broad Slack/Telegram history, GitHub PR/CI integration, and external writes.

### Iteration 3: optional Microsoft 365 and daily summary

**Outcome:** After separate approval and authentication, Outlook mail/calendar can contribute read-only inbox candidates and the existing 9:30 AM job can deliver a concise daily summary.

**Includes:** pinned connector, least-privilege tool allowlist, read-only smoke tests, scheduled refresh, last-good fallback, and current-destination delivery.

**Defers:** sending mail/messages, moving mail, editing calendar events, automatic desktop notifications, and any custom Microsoft Graph client.

### Iteration-to-slice mapping

Iteration 1 = Slices 1–3. Iteration 2 = Slices 4–5. Iteration 3 = Slices 6–7. Slice 8 (real data import and final verification) closes out all iterations and is not itself gated by iteration boundaries.

## 8. Risks and mitigations

### Scope expansion from “todo” into a universal inbox

**Risk:** Integrations dominate the project before the core task loop is useful.

**Mitigation:** Ship Iteration 1 without integrations. Treat every source as optional and require confirmation before persistence.

### Duplicate or noisy source candidates

**Risk:** Similar mail, chat, project, and calendar signals flood the Inbox or merge incorrectly.

**Mitigation:** Deterministic caps, fingerprints, source badges, manual split, persistent handling state, and fixture coverage for resurfacing rules.

### Repository privacy

**Risk:** Tracked operational data includes sensitive email/chat content.

**Mitigation:** Store only action summaries, provider ids, fingerprints, and links; exclude full bodies/transcripts; keep the repository private; scan before commit.

### Microsoft tenant consent and connector trust

**Risk:** UNL blocks delegated scopes, or a community connector exposes more capability than intended.

**Mitigation:** Keep Microsoft 365 optional, pin the reviewed version, filter on both sides, use read-only scopes, inspect the exposed tools, keep tokens local, and require separate installation consent.

### Desktop compatibility patch drift

**Risk:** The portable Ask Hermes patch stops applying after Hermes updates.

**Mitigation:** Keep the composer bridge tiny and generic, forward/reverse-check it against live and clean worktrees, and feature-detect it in the disk plugin.

### Refresh cost and duplicate runs

**Risk:** Pane-open refreshes repeatedly collect the same sources or start overlapping work.
